# M4.5 — Local AI sandbox and Jend Net Broker

Status: architecture/prototype. Not production-audited.

## Goal

A local model may use internet-backed tools without receiving raw network access.
The inference process is treated as potentially compromised by malformed model
artifacts, parser/runtime bugs or prompt-injection content.

## Hard rule

`Local AI` has **no raw sockets, DNS, connect(), listen(), arbitrary process
execution or unrestricted filesystem access**.

Internet access is brokered:

```text
Local AI (no network)
        |
        | typed tool request / encrypted local IPC
        v
Jend Net Broker
        |
        | policy + capability + URL/target validation
        v
TLS 1.3 / HTTPS
        |
        v
Public Internet
```

Encryption and authorization are separate controls. TLS/JNET protect bytes in
transit, while broker policy decides which bytes may leave the device.

## No arbitrary URL primitive for the model

An unrestricted `fetch(url)` is rejected as a security boundary because a
compromised model can encode private data into a path/query even when HTTPS is
perfect.

Preferred tool shapes:

1. `Search(query)` — explicitly internet-facing user action.
2. Search results are stored by the broker and returned with opaque handles.
3. `Open(handle)` — the model opens only an exact broker-issued target.
4. External APIs use typed connector adapters with fixed endpoint templates.
5. API credentials are held/injected by the broker or dedicated credential
   helper and are never placed in the model context.

Direct arbitrary navigation, if ever supported, requires a separate explicit
policy grant and should not be the default agent primitive.

## SSRF / rebinding protection

The broker core requires:

- HTTPS only;
- no URL userinfo credentials;
- default port 443 in the baseline;
- reject localhost, private, link-local, CGNAT, multicast, documentation,
  benchmarking and other special-use address ranges;
- resolve DNS, validate **every** returned IP, then connect to one of those
  exact validated IPs while preserving the original hostname for TLS SNI and
  certificate verification;
- never re-resolve between validation and connect;
- re-run the full check for every redirect;
- small redirect count;
- strict compressed/decompressed response-size budgets;
- no `file:`, `data:`, `ftp:`, `gopher:` or custom schemes.

This blocks common paths to `127.0.0.1`, RFC1918 networks and cloud metadata
endpoints such as `169.254.169.254`.

## Web content is tainted data

Downloaded pages are always labelled `UntrustedInternet`. Text from a page can
never itself grant tool permission, modify the DeviceSet, unlock Vault keys,
install a model, approve recovery, or create a broader network capability.

Tool authorization is enforced outside the model.

## Process sandbox target

### Linux baseline

- dedicated unprivileged UID;
- isolated network namespace with no interfaces for `Local AI`;
- `no_new_privs`;
- seccomp allowlist, default deny;
- Landlock/mount namespace restricting filesystem to model files, bounded
  scratch space and explicit IPC endpoints;
- no `ptrace`, mount, namespace creation, raw device access or arbitrary exec;
- cgroup CPU/memory/PID limits;
- read-only model artifact after verification;
- no model-defined native plugins/custom operators.

GPU access is a special risk because a GPU device/driver expands the kernel
attack surface. The stronger future design is a minimal GPU broker or narrowly
scoped device access rather than exposing every accelerator device node to the
model process.

Equivalent Windows/macOS/mobile profiles are required before production.

## JNET local encryption

`jend-net-broker` contains an XChaCha20-Poly1305 sequence-bound local IPC frame.
It protects local IPC confidentiality/integrity and rejects replayed sequence
numbers. It does **not** turn a compromised holder of the session key into a
trusted process; policy remains the authorization boundary.

## Internet privacy limits

For an arbitrary public website, the destination necessarily receives the
request content intended for it. Jend cannot make that plaintext invisible to
the destination while still asking that destination to answer it.

A future privacy mode may use a split ingress/egress relay (or standardized
oblivious/multi-hop transport) so no single relay learns both account identity
and destination. That is a separate privacy feature, not a replacement for the
local sandbox.
