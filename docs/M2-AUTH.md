# M2 — Account authentication baseline

Status: implementation draft; compile/integration testing intentionally deferred to the dedicated test milestone.

## Product requirements

The public account identity contains only:

- globally unique username;
- password known only to the user/client;
- optional one-time recovery code generated by the client.

No email address and no phone number are required.

## Username policy

The initial security identifier is deliberately conservative:

```text
[a-z0-9_]
3..24 bytes
no leading/trailing underscore
case-insensitive canonicalization
```

`Alice_7` and `alice_7` are therefore the same account. Unicode usernames are deferred because confusable characters create account-impersonation and moderation problems. A future non-unique display name can support Unicode without becoming a security identifier.

## Password authentication: OPAQUE

Jend uses an OPAQUE aPAKE flow rather than sending a plaintext password to the application server.

High-level registration:

```text
no-network client auth component             server auth

password
  |
OPAQUE client start
  +------ RegistrationRequest ------------->
  <------ RegistrationResponse -------------+
  |
OPAQUE client finish
  +------ RegistrationUpload -------------->
                                             opaque password file stored
```

High-level login:

```text
password
  |
OPAQUE client start
  +------ CredentialRequest --------------->
  <------ CredentialResponse ---------------+
  |
OPAQUE client finish
  +------ CredentialFinalization ---------->

client and server derive authenticated session material
```

The password itself is not an application-layer field sent to the Jend server. The server persists the OPAQUE password file.

## Stateless edge login tickets

The transient server login state is sealed into a short-lived AEAD ticket. This avoids requiring Redis merely to remember incomplete handshakes.

The final request contains:

```text
opaque login ticket
+
CredentialFinalization
```

The edge decrypts the ticket, restores the OPAQUE state and completes the protocol.

## Unknown-user login

The server uses OPAQUE's dummy/unknown-user path instead of returning a trivially different cryptographic response when no password file exists.

The global username namespace is intentionally public, so this is protocol hygiene rather than an attempt to make usernames secret.

## Recovery without email or phone — revised M2.1

The first draft used a domain-separated SHA-256 recovery verifier. That design has been removed.

A hash is not "decryptable", but any verifier derived directly from human/predictable input can become an offline guessing target. Jend therefore avoids storing a bare recovery hash/verifier.

The recovery code is now 256 bits of OS-CSPRNG entropy and is domain-separated locally before entering a **second OPAQUE credential flow**.

Recommended server layout:

```text
normal AuthServer setup
  -> password OPAQUE record

independent RecoveryAuthServer setup
  -> recovery OPAQUE record
```

The two OPAQUE server setups/keys must be cryptographically and operationally separated.

The server therefore stores an opaque recovery credential record, not:

```text
SHA256(recovery_code)
```

## Account recovery is not data recovery

Recovering the login account must not automatically decrypt old conversations.

```text
account recovery != conversation-data recovery
```

Multi-device history access is authorized by trusted-device key transfer (`jend-sync`). A future persistent-cloud recovery feature will require separate user-controlled data-recovery key material.

## Process boundary

Password/recovery OPAQUE **client** operations run only in a no-network local trusted component (Vault or dedicated auth helper). The Network process transports only protocol messages and opaque tickets.

## Minimal database shape

```text
accounts
  user_id
  username_canonical UNIQUE
  opaque_password_file BYTEA
  opaque_recovery_file BYTEA NULL
  created_at
  status

devices
  device_id
  user_id
  public identity metadata
  created_at
  revoked_at NULL
```

The server-side device table is administrative/routing state. For encrypted chat synchronization, the client-signed `DeviceSet` is the cryptographic source of trust; a database administrator cannot make a device trusted merely by editing this table.

There is still no `messages` or `prompts` table.

## Still required before production

- independent persisted OPAQUE setup/ticket keys for password and recovery domains;
- benchmark/freeze Argon2 profile;
- rate limits and adaptive anti-bot admission;
- bind initial device enrollment to authenticated account creation;
- short-lived signed application capabilities;
- password-change and recovery-rotation flows;
- compile, integration, property and fuzz testing.
