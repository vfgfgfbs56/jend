# M4.8 shared admission backstop

Added migration 002 and corrected the transactional quota algorithm.
It permits five successful challenge consumptions per 60-second fixed window
for each opaque bucket key; the sixth is rejected. Concurrent calls serialize
on PostgreSQL row locks. Replayed challenge IDs are rejected via unique index;
the quota debit rolls back if replay is detected.

**Not yet production ready.** This is a shared DB backstop, not the full
anti-bot system. The endpoint remains fail-closed (`503`) until the signed
challenge, proof-of-work, proxy-authenticated client identity, OPAQUE
registration/login, and capability issuance are connected. A coarse fixed
window allows bursts at window boundaries. Use an independent edge limiter.
Do not derive a rate key from untrusted client headers.

No cargo or PostgreSQL execution was available in this environment;
compilation and database concurrency tests remain pending.
