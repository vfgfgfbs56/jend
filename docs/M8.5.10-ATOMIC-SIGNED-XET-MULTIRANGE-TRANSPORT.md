# M8.5.10 — Atomic signed Xet multi-range HTTPS transport

## Scope

The Xet metadata planner already emits a `SignedRangeBatchRequest` for **one**
fetch entry with several signed physical ranges. M8.5.9 validates a bounded
multipart/byteranges body. M8.5.10 joins those boundaries into an callable
network path while retaining the original `SingleRange206` comma rejection.

```text
validated reconstruction
    -> bounded scheduler (one entry stays atomic)
    -> SignedRangeBatchRequest
    -> revalidate hash/host/path/ranges/header/payload sum
    -> pinned public-IP HTTPS, TLS/SNI, no proxy/redirect
    -> HTTP 206 only, identity encoding, bounded response
    -> strict multipart body + exact Content-Range parts
    -> UntrustedXorbPhysicalRange with exact chunk binding
    -> STOP (no WeightVM admission)
```

## Security properties

- The entrypoint accepts a typed request from the strict Xet metadata parser,
  not a user-supplied arbitrary URL.
- Before network I/O it revalidates signed URL host/path/hash, the exact
  comma-separated Range header, aggregate physical byte count, overlapping
  spans, chunk-span validity and part-count limits.
- The original entry must stay atomic. It is **never** split into single-range
  requests or a best-effort full-object download.
- The HTTP transport only accepts **206 Partial Content**, never 200; follows
  no redirects, sends no Hub bearer token to xorb origins, and requires public
  pinned DNS results with HTTPS identity verification.
- Multipart response headers must contain exactly one Content-Type and no
  Content-Encoding or top-level Content-Range. `Accept-Encoding: identity`
  avoids content transformations while handling physical byte offsets.
- Per-entry payload is hard-capped at 16 MiB, framing overhead at 128 KiB,
  and the maximum number of parts at 512. Timeouts and total response size
  retain independently bounded transport limits.
- The strict parser rejects duplicates, missing/extra parts, invalid
  Content-Range/length, unexpected headers, malformed boundaries and data
  exceeding either budget.
- The result is `UntrustedXorbPhysicalRange` indexed by exact Xorb
  hash/chunk spans, **not a verified model page**.
- Signed URLs and tokens must never be logged. Errors intentionally contain
  no URLs or raw bytes.

## Tests and verification

New offline tests cover typed authorization mutation, canonical Range-header
binding, overlapping physical descriptors, HTTP 200 fallback, MIME corruption,
truncated bodies, budgets, top-level header injection and physical
chunk-to-range binding.

Run on Mac (no HF token required):

```bash
bash scripts/first-test-ladder.sh
bash scripts/dev-xet-fetch-schedule-smoke.sh
```

The smoke additionally prints:

```text
Jend Xet atomic signed multi-range response gate: PASS
Jend Xet HTTP 200 fallback rejected: PASS
```

These tests simulate an HTTP status and response body. They **do not prove a
successful live multi-range HF/Xet fetch**, nor do they exercise remote malicious
server behavior. GitHub CI validates build/test when green, not live network.

## Deliberately not implemented

- A live opt-in HF/Xet multi-range probe with a real signed fetch entry and
  explicit per-request byte budget.
- Multi-entry bounded network waves, cancellation, retries/backoff, or
  aggregate response-framing budget across jobs.
- Pipelining the returned physical ranges through bounded xorb decode and
  `reconstruct_slice_from_ranges(...)` into independent Jend-signed pages.
- Independent release-signed WeightPage SHA-256/exact-length gate, durable
  object publication and WeightVM admission.
- Source-adapter trait, local/publisher/mirror resolver and Source Sandbox.

High-level **M8.5 remains incomplete** until a full independent signed page
path across multiple eligible source types is proven.
