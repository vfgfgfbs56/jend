# Jend sync relay — minimal server protocol draft

The server is deliberately ignorant of conversation semantics.

## Immutable object API

```text
PUT /v1/sync/object/{object_id}
GET /v1/sync/object/{object_id}
```

`object_id` is a random 256-bit value generated by the client. The body is a `JESO` encrypted object.

Rules:

- create-only; overwriting an existing object ID fails;
- server never parses decrypted fields because it has no key;
- strict maximum object size;
- account quota is enforced by authenticated capability, not message contents;
- object IDs from another account must not be oracle-probeable.

## Opaque head pointer

```text
GET /v1/sync/head
PUT /v1/sync/head
```

The value is only the latest encrypted index object ID. Updating uses compare-and-swap/ETag so concurrent devices can detect races and merge locally.

The semantic `index_generation` stays encrypted inside the index and is remembered locally by Vault.

## Temporary relay mailbox

```text
POST /v1/relay/mailbox
PUT  /v1/relay/mailbox/{random_token}
GET  /v1/relay/mailbox/{random_token}
DELETE /v1/relay/mailbox/{random_token}
```

Used for device-approval/key envelopes and offline deltas. Mailboxes are random, short-lived, quota-limited and contain opaque bytes.

## Authorization

The future gateway issues short-lived signed capabilities after OPAQUE account authentication. A capability should contain only the minimum server-visible policy:

```text
account_id
expiry
max object bytes
max temporary mailbox bytes
operations bitset
nonce / replay scope
```

Capabilities do not contain conversation IDs or model/chat metadata.

## Cost-oriented implementation

Initial deployment can use:

```text
Rust gateway
PostgreSQL: account + tiny pointer/quota rows
R2-compatible object storage: encrypted immutable objects
```

The server should not perform per-message database writes beyond object/pointer accounting. A future sync-segment format should bundle multiple DAG nodes to reduce object-store operation count.
