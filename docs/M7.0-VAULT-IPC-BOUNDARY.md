# M7.0 — Vault IPC boundary: first hardening checkpoint

## What exists
- `jend-vaultd` is a separate process using Unix-domain sockets.
- The Vault owns AccountRootKey, device signing/KEX secrets, plaintext and
  encrypted local storage. The network gateway does not receive these secrets.
- IPC uses a versioned, length-bounded binary request format.
- Socket mode is `0600`, and the socket parent directory must already be private
  (`0700` or more restrictive). A newly created parent inherits system umask;
  if it is not private, startup fails rather than silently relaxing policy.
- An existing socket path, including a symlink or a stale socket, is never
  automatically removed. This prevents accidental replacement of another
  process's listener.

## macOS development run
Choose a private socket directory:

```sh
mkdir -p "$HOME/.jend-dev/ipc"
chmod 700 "$HOME/.jend-dev/ipc"
export JEND_VAULT_SOCKET="$HOME/.jend-dev/ipc/vault.sock"
export JEND_VAULT_STATE_DIR="$HOME/.jend-dev/state"
export JEND_VAULT_SECRET_DIR="$HOME/.jend-dev/secrets"
cargo run -p jend-vault --bin jend-vaultd
```

`DevFileSecretStore` is explicitly development-only, not a production
Keychain/Secure Enclave integration. Never run this daemon with a public socket
directory or expose its socket to untrusted local users.

## Remaining M7 work
This is *not* a complete authenticated IPC boundary. The next checkpoint
must add peer identity checks, request authorization, timeouts and bounded
work queues; later milestones add durable OS-backed key storage and a UI
client that never holds Vault secrets. This checkpoint does not claim that
local malware running as the same user is isolated from the Vault.
