# M5.2 — JREQ request proof (cryptographic core)

This stage introduces `crates/jend-jreq`: a domain-separated canonical
Ed25519 signed request including method, exact path/query, SHA-256 body digest,
SHA-256 capability token digest, device ID, 256-bit nonce and timestamp.
A PostgreSQL migration defines per-account/device nonce uniqueness.

## Required verification order in the HTTP Gateway
1. Verify the JCAP issuer signature, expiry, permissions and auth epoch.
2. Load current signed DeviceSet and ensure device membership and trust epoch.
3. Verify the JREQ Ed25519 signature with the *current* device public key.
4. Atomically insert the nonce **before** performing the requested side effect.
5. Check authorization for the requested resource, then execute it.
6. Reject any DB outage (fail closed). Do not log signatures, tokens or body.

## Remaining before activation
- HTTP middleware extraction of the *exact* request target and raw body.
- Ensure all front proxies preserve/canonicalize request target consistently.
- Connect nonce insertion to the HTTP middleware with PostgreSQL.
- Refresh capability flow, revocation, session lifecycle and rollback defense.
- Validate against actual `ed25519-dalek` API with `cargo check` and tests.
- Nonce garbage collection must retain records past the full accepted window.
- Never trust a client-supplied device ID without matching the verified JCAP.

This stage is a **library and schema**, not deployed enforcement.
Existing protected routes must not be considered JREQ-protected yet.
