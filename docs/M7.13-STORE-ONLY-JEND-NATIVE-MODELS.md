# M7.13 — Store-only execution and Jend-native model blueprint

Jend's product direction is now explicit:

- end users choose models only from Jend Store;
- public Store models do not execute through external model-provider APIs;
- selectable models are local packages, VirtualPaged models, or future
  Jend-native releases backed by those same local/WeightVM execution paths.

`ProviderRemote` remains only as a historical/admin catalog representation so
older data structures do not need to be destructively migrated. Public Store
activation and chat execution reject it fail-closed.

## What "similar to Claude/GPT" means for Jend

Jend may build models that target the same broad capability classes:

- reasoning;
- coding;
- long context;
- tool use;
- multimodal understanding;
- writing.

That is not the same as duplicating a restricted closed model.

A Jend-native model is built from sources whose training rights are approved:
open/licensed weights and datasets, Jend-owned synthetic data, human-authored
data, and other permitted sources. A teacher may be:

- Jend-owned; or
- explicitly licensed for training/distillation.

A restricted closed provider service without explicit training rights is not an
allowed teacher. Renaming the resulting model would not change that provenance
problem.

## Native sparse blueprint

`JendNativeBlueprint` describes a future model as composable parts:

```text
shared backbone
      |
    router
      |
  expert groups  <-- pageable by WeightVM
      |
 adapters / long-context / tool modules
```

This is intentionally aligned with the future Model Fabric. A large logical
model can place most parameters in independently pageable expert groups while
keeping a smaller shared backbone/router resident.

The first deterministic blueprint smoke represents roughly 100.1B logical
parameters, 96B of which are pageable experts. The number is a contract test,
not a claim that such a model has already been trained.

## Why we keep capability evaluation separate

Closed frontier models may be useful as public market references for humans,
but Jend training/evaluation infrastructure must not silently turn them into a
training oracle. Our actual model-development loop should use public benchmarks,
licensed datasets, Jend-owned evals, human review, and our own previous models.

## M8 direction

This unlocks two parallel research tracks:

1. **Model Fabric / WeightVM** — make enormous sparse models practical on user
   devices through paging, quantization and residency management.
2. **Jend Native Models** — design/train our own sparse models whose active
   working set is intentionally small enough for those devices.

The second track is important: WeightVM alone cannot make an arbitrary dense
frontier model require only tens of megabytes. To reach the desired product
experience, model architecture and runtime must be co-designed.
