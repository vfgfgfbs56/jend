# M8.5.15.6b.2 — inherited file-descriptor and environment probe

**Status:** Linux-only, model-free, dev-only. **Does not authorize** inference,
production worker execution, handling E2EE secrets or filesystem access.
macOS and Windows deliberately reject this Linux-only sandbox mode.

## Threat

Linux seccomp can block `openat` after installing the filter, but any
**already-open inherited file descriptor** could still read a user's
private file, even when opening new files returns `EPERM`. Environment
variables can likewise unintentionally inherit tokens. M8.5.15.6b.1
did not test these preexisting capabilities.

## What the code changes

- The Python offline harness creates a **nonsecret canary file**, opens it
  before launching the model-free worker and intentionally passes that
  real FD into the Linux process via `pass_fds=(fd,)`.
- The harness passes a synthetic `JEND_TEST_INHERITED_ENV_CANARY` via
  an explicitly minimized environment. It does **not** forward the actual
  user's environment, API tokens or private files to a native worker.
- The Linux-only `--sandbox-probe --deny-read <path> --inherited-fd <fd>`
  entrypoint requires the FD really is open; malformed, missing or fake
  values fail closed.
- Linux `close_range(3, ~0u, 0)` closes **all** non-stdio descriptors
  in one kernel operation before the seccomp filter. Unsupported syscall
  or kernel, invalid fd, or cleanup failure means refusal — never fallback.
- `clearenv()` clears the inherited synthetic environment; the worker
  explicitly confirms that the canary variable is no longer present.
- After installing existing `no_new_privs`, seccomp BPF and hard RLIMITs,
  the exact formerly inherited FD must still return `EBADF` from
  `fcntl(F_GETFD)`. The prior actual `EPERM` checks for a new
  `openat`, socket and fork remain in force.
- The command's success marker remains `JEND-LINUX-RESTRICTED-PROBE-V1`
  **only** if every test passes. Missing/false descriptor refuses.

## Critical limitations (NO-GO)

This is an **in-process check after the executable has begun running**.
Any startup code before cleanup can access inherited files or environment
variables. A malicious worker can ignore these functions entirely.
Stdio `0,1,2` remains inherited; these streams may carry secrets unless
the trusted parent verifies exactly which pipes and handles it passes.
Memory mappings, process arguments, GPU drivers and other resources are
not isolated by `close_range` or `clearenv`.

It is NOT a trusted launcher, complete seccomp syscall allowlist,
Landlock/mount namespace filesystem isolation, dedicated UID, signed
worker binary, process-tree supervisor or sealed GGUF/WeightVM handoff.
The test is compiled with `JEND_BUILD_EXPERIMENTAL_LLAMA=OFF` and does not
load real models. No E2EE data, passwords or tokens should be supplied.

**JSEC-001 remains Critical / OPEN.** Production must create a trusted
parent-broker that constructs a clean environment *before exec*, closes
unintended FDs atomically before/at exec, supplies only approved pipes and
verified immutable weight handles, and enforces OS sandbox, resource
budgets and signed executable identity. Windows and macOS require
separate native isolation implementations and actual device tests.

## Offline test

```bash
python3 scripts/dev-native-linux-seccomp-probe.py
```

On Linux x86-64 and ARM64 the previously proven socket/file/fork and
resource PASS lines remain, plus:

```text
Jend Linux close_range removes inherited canary descriptor: PASS
Jend Linux clearenv drops synthetic inherited environment: PASS
Jend native absent inherited descriptor fail-closed: PASS
```

On macOS and Windows, only the unsupported-mode refusal and common
negative tests PASS. They **do not** prove Linux cleanup or Mac/Windows
sandboxing. Updated root `JEND-PROJECT-CONTEXT.md` and
`JEND-SECURITY-REGISTER.md` distinguish these results.
