# M6.1 — RustCrypto API compatibility hardening

This checkpoint fixes a concrete source-level incompatibility with
`chacha20poly1305 0.11.0`. The 0.11 release exposes the crate-level `Key` as a
fixed 32-byte alias rather than the older generic form used by the repository.
The previous source contained 18 constructions of the form
`Key::<XChaCha20Poly1305>::from_slice(...)`; those are incompatible with the
0.11 API.

All affected code in `jend-core`, `jend-auth`, `jend-sync`, and
`jend-net-broker` now constructs the cipher through
`KeyInit::new_from_slice(...)`. The key inputs at these call sites are fixed
32-byte arrays/zeroizing arrays, so the remaining `expect` represents an
internal invariant rather than validation of attacker-controlled lengths.

Nonce references were also moved from deprecated `XNonce::from_slice` to the
current hybrid-array conversion API. `scripts/static-preflight.py` rejects both
old forms if they are reintroduced.

A second compile-time incompatibility was found in `jend-auth`. `hkdf 0.13.0`
uses the current RustCrypto digest generation and its published examples use
`sha2 0.11`, while `opaque-ke 4.0.1` still depends on `digest 0.10` and uses
`sha2 0.10` for its documented cipher suite. A single `sha2` dependency cannot
satisfy both type-level trait graphs. `jend-auth` now uses `sha2 0.11.0` for
recovery HKDF and a renamed `sha2_10` package dependency (`0.10.9`) exclusively
for OPAQUE's `TripleDh<..., Sha512>` suite. The dependency-policy script now
understands Cargo package aliases and validates the underlying package name.

The OPAQUE 4.0.1 server/client calls used by `jend-auth` were cross-checked
against the published API shape (`ServerRegistration::start/finish`,
`ServerLogin::start/finish`, Argon2 feature/re-export). No source change was
needed there.

## Supply-chain wording correction

M6.0 introduced an allowlist for direct dependency *requirements*. It did not
fully freeze the graph: requirements such as `tokio = "1"` and `sqlx = "0.8"`
still allow compatible releases, and transitive dependencies remain unresolved
until Cargo generates `Cargo.lock`. A revision is only reproducibly dependency-
locked after the real Cargo runner generates and retains that lockfile.
