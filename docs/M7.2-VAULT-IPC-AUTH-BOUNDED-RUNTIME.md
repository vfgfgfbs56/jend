# M7.2 — Vault IPC capability authorization and bounded runtime

M7.2 adds a per-daemon 256-bit IPC capability and a bounded worker front-end.

## Security boundary

- Every IPC request carries a fresh-per-daemon 256-bit capability.
- The Vault compares it in constant time before parsing/executing a Vault
  operation.
- The capability is written as a `0600` regular file inside the already-private
  `0700` IPC directory.
- The daemon refuses to overwrite a stale/existing authorization path.
- Private AccountRootKey/device keys never cross IPC.

This is a practical local client authorization step, not a claim of protection
against arbitrary malware already executing as the same OS account. Rust 1.99's
standard Unix peer-credential API remains unstable, and Jend keeps
`#![forbid(unsafe_code)]`; stronger platform launcher/attestation integration is
therefore a later explicit milestone rather than an unsafe shortcut.

## Responsiveness / old-device behavior

The daemon no longer lets an unbounded number of clients create threads or
queue memory:

- 4 fixed IPC workers;
- queue depth 32;
- 5-second socket read/write deadlines;
- over-capacity connections are dropped immediately;
- a worker reads and authenticates the complete bounded request before taking
  the Vault mutex.

This is the first concrete runtime property tied to Jend's "instant UI"
requirement: malformed or slow IPC clients cannot hold the Vault lock while
dribbling a request byte-by-byte.

## Test

After `first-test-ladder.sh`:

```sh
bash scripts/dev-vault-ipc-smoke.sh
```

The smoke now also replaces only the client-visible capability with an invalid
one and proves the live daemon rejects it, then restores the correct capability
and completes the restart/durability checks.
