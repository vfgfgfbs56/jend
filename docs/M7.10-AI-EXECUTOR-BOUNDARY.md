# M7.10 — AI Executor Boundary

M7.10 introduces the first separate local AI process, `jend-aid`.

## Security boundary

`jend-aid` is built inside the existing `jend-model-store` package only to keep
our proven Cargo.lock dependency graph unchanged. It is a separate OS process
and the package has no `reqwest`, `hyper`, `tokio`, URL client, or `jend-vault`
dependency. The model-store library still stores only scheduling/model metadata;
prompt bytes exist only inside the daemon binary in `Zeroizing<Vec<u8>>`.

A later architecture-freeze step may move the binary into a dedicated crate when
we intentionally reset the workspace lock baseline. Process isolation is the
security boundary; the current packaging is a lock-file compatibility choice.

## IPC

The daemon uses a Unix-domain socket:

- private parent directory (`0700` or stricter);
- socket `0600`;
- fresh per-daemon 256-bit capability file `0600`;
- constant-time capability comparison;
- 5 second client I/O deadlines;
- 8 MiB hard input bound;
- bounded two-worker IPC queue;
- refuses to replace an existing socket/auth path.

## AI scheduling

`AiExecutor<T>` provides:

- bounded, non-blocking submit/backpressure;
- fixed physical worker ceiling;
- dynamically adjustable active-worker and queue limits;
- queued cancellation;
- cooperative cancellation markers for active jobs;
- no force-kill of an in-flight backend kernel;
- explicit finish bookkeeping.

This matches the M7 runtime policy: thermal/low-power changes will update the AI
process limit at safe task boundaries rather than allowing model work to block
UI or Vault operations.

## Current placeholder processing

M7.10 deliberately does **not** pretend to contain a real LLM backend. The
process smoke hashes a bounded input inside AI worker memory. This proves IPC,
authentication, zeroizing ownership, worker bounds and process separation. The
next backend milestone will replace the digest operation with an inference
backend adapter while retaining the same boundary.
