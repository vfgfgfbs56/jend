# M8.5.4 — First live signed Xet xorb single-range fetch

M8.5.4 performs the first real Xet payload request in Jend, but deliberately
stops before decoding or publishing model bytes.

## Safety boundary

The live smoke repeats the already-proven immutable Hub resolve, scoped Xet
read-token and CAS v2 reconstruction query for `bytes=0-0`. It then executes a
signed xorb fetch only when the selected reconstruction fetch entry contains
**exactly one** physical byte range.

The HTTP `Range` header is derived solely from validated
`xorbs[hash][].ranges[].bytes`; it is never caller supplied. The transport:

- resolves and validates public IPs before connecting;
- pins those IPs while retaining the original hostname for TLS/SNI;
- disables proxies and redirects;
- accepts only existing exact HF/Xet source hosts;
- requires HTTP 206 for the xorb request;
- rejects a 200/full-object fallback;
- requires the response body length to equal the requested inclusive range;
- caps the live smoke at 16 MiB;
- never logs the signed URL/query;
- does not persist or pass the raw xorb body to WeightVM/inference.

Multi-range fetch entries remain fail-closed. They require a strict
`multipart/byteranges` parser and are intentionally deferred.

## Not claimed yet

The fetched bytes are raw serialized/compressed xorb data. M8.5.4 does **not**
deserialize xorb chunks, decompress them, verify reconstruction-term unpacked
lengths, reconstruct the requested file byte, hash a WeightPage, or write the
durable WeightVM store. Therefore a successful M8.5.4 fetch is transport proof,
not model-weight integrity proof.
