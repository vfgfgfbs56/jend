# M5.0 — OPAQUE HTTP authentication gateway

## Implemented

- `POST /v1/registration/admission` issues a short-lived signed, username-bound `JADM` challenge.
- `POST /v1/auth/register/start` verifies signature/expiry/PoW and atomically consumes the challenge before OPAQUE registration start.
- `POST /v1/auth/register/finish` verifies the encrypted auth ticket, finishes OPAQUE, and persists only the OPAQUE password file.
- `POST /v1/auth/login/start` uses OPAQUE's unknown-user path and shared PostgreSQL rate limits (per network and per canonical username).
- `POST /v1/auth/login/finish` finishes OPAQUE, one-time-consumes a digest of the login ticket, then returns a five-minute signed account capability.
- `GET /readyz` verifies the required auth schema exists.
- Raw IP addresses are not persisted; rate keys are HMAC-derived with a server secret.
- Request bodies are capped; binary protocol messages are base64url encoded with per-field limits.

## Persistent server secrets

`jend-keygen <new-dir>` creates a private directory containing:

- `opaque-server-setup.bin` — long-lived OPAQUE ServerSetup; losing/rotating it breaks password authentication for existing password files.
- `auth-ticket.key` — XChaCha20-Poly1305 key for short-lived auth tickets.
- `capability-ed25519.key` — online capability signing key.
- `admission-ed25519.key` — registration challenge signing key.
- `rate-hmac.key` — privacy-normalization key for rate buckets.

The gateway refuses group/other-readable Unix secret paths and rejects symlinks. It does not generate replacement secrets on startup.

## Threat-model notes

- Account capability is intentionally short-lived and not yet device-bound. Its only purpose is device enrollment/account bootstrap. Normal sync/model access must use a trusted-device capability.
- Registration username availability is observable. Usernames are public routing identities in the current threat model.
- The current reverse-proxy identity model uses the TCP peer address. Do **not** trust `X-Forwarded-For`/CF headers until origin authentication (mTLS or equivalent) is implemented. Behind a proxy this means rate limiting sees the proxy, so production edge integration remains required.
- Shared DB windows are abuse backstops, not a full bot-defense system. Edge velocity controls and adaptive risk signals still need production integration.
- Expired replay rows require a bounded cleanup job; never delete unexpired rows.

## Not verified in this environment

No Rust toolchain or PostgreSQL server is available here, so this milestone has not been compiled and migrations have not been executed. Required next: compile, DB concurrency tests, an OPAQUE client/server end-to-end test, malformed-message fuzzing, and proxy/rate-limit abuse tests.
