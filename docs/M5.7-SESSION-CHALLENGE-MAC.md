# M5.7 — server-bound trusted-device session challenges

A security preflight found that the M5.6 trusted-device session flow accepted a
fresh `DeviceSessionChallenge` based only on the trusted device signature. A
holder of a device private key could therefore construct the challenge locally
and bypass `/v1/auth/device/session/start` and its rate limit.

M5.7 makes `/session/start` mandatory:

1. gateway creates the challenge;
2. gateway returns `challenge_mac = HMAC-SHA256(device-session-hmac.key, domain || challenge)`;
3. the device signs the challenge;
4. `/session/finish` verifies the server MAC **before account lookup**;
5. it verifies current DeviceSet membership and the device signature;
6. it atomically consumes the challenge digest as a replay barrier before issuing a capability.

The smoke CLI deliberately flips one bit in `challenge_mac` and requires HTTP
401 before trying the valid request. It also retains the proof-replay test.

## Secret directory compatibility

M5.7 adds `device-session-hmac.key`. Development secret directories generated
by an older `jend-keygen` are intentionally rejected by startup. Delete the
old **development-only** secret directory and run the current `jend-keygen`
again. Production secret rotation/migration needs an explicit operational
procedure before deployment.

## Static preflight

`scripts/static-preflight.py` now validates migration numbering/table presence,
CLI/server route agreement, JREQ enforcement on implemented sensitive device
routes, atomic nonce+DeviceSet CAS, and the device-session MAC/keygen contract.
It runs before Rust compilation in CI.

This is still not a claim that `cargo check`, unit tests, or the PostgreSQL smoke
flow have passed in the ChatGPT execution environment; no Rust/PostgreSQL
runtime is available here.
