# M4.5 — Control plane and application capabilities

Status: transport-independent implementation baseline, pre-test/pre-audit.

The control plane exists to authenticate accounts, authorize currently trusted
devices, manage model entitlements and route opaque sync objects. It must never
become a chat decryption authority.

## Two-stage authority

A successful OPAQUE password login yields only a short-lived **account
capability**. It can manage the account, begin device enrollment and read the
public model catalog, but it is not sufficient for sync relay or model download.

```text
OPAQUE login
    |
    v
account capability
  ACCOUNT_MANAGE
  DEVICE_ENROLL
  MODEL_CATALOG
    |
    | server challenge bound to capability nonce
    v
Vault-held trusted device signs challenge
    |
    v
device-bound capability
  SYNC_RELAY
  MODEL_DOWNLOAD
```

This prevents an API/database attacker from turning an arbitrary `device_id`
column into cryptographic device authority.

## Capability tokens

`jend-capability` defines short-lived Ed25519-signed tokens containing:

- account ID;
- `auth_epoch`;
- optional device ID;
- issued / expiry times (maximum one hour at the primitive layer);
- explicit permission bits;
- random nonce.

Edge nodes can verify these locally with the public capability-verification key,
so ordinary authenticated requests do not require a PostgreSQL lookup solely to
validate a session token.

The capability key is a server authorization key. It cannot decrypt `.jend`,
JESP objects or Vault state.

## `auth_epoch`

Password rotation/recovery increments `auth_epoch`. A service that needs strong
revocation compares the capability epoch with the account's current minimum
accepted epoch (locally cached or refreshed according to service policy).

A token from an older epoch is rejected even if its Ed25519 signature is valid.

## Persistence boundary

`jend-control` deliberately exposes small persistence traits for:

- password-reset grant consumption + OPAQUE credential replacement;
- signed DeviceSet compare-and-swap;
- three model entitlement slots;
- model catalog manifests;
- per-device installation bookkeeping.

There is intentionally no persistence method such as `load_message`,
`conversation_plaintext`, `conversation_key`, or `decrypt_sync_object`.

## Model download authorization

The gateway checks all of:

1. a current device-bound application capability;
2. current DeviceSet membership;
3. account model entitlement/slot and entitlement epoch;
4. signed model manifest matches the selected model.

Only then does it issue a short-lived device/model/manifest/slot-bound download
grant. CDN/object-storage possession alone is not release authority; the client
still verifies the offline signed manifest and chunk/whole-model hashes.
