# M7.7 — Model Store access architecture

Jend Store is not defined as "a list of downloadable weight files". A catalog
entry represents a model capability with one of three delivery modes.

## 1. LocalPackage

For open or appropriately licensed weights, Jend distributes a signed,
chunk-addressed release. The entitled device downloads and verifies the model,
then inference remains local.

## 2. ProviderRemote

For a closed model whose weights are not distributed, Store installs a provider
binding rather than pretending the weights can be downloaded. The binding names
the provider/model and credential mode. Credentials themselves are not public
catalog metadata.

This is the correct path for Claude-like closed models unless the publisher
grants Jend explicit weight-distribution rights. Jend can support user-managed
provider credentials, provider-account authorization, or a commercial
pass-through agreement. The last option is a business contract, not free
inference and not hidden Jend hosting.

## 3. VirtualPaged

For extremely large open/licensed models, Store installs a signed virtual model
index and a bounded local cache rather than requiring a full eager install.

The model records:

- logical weight bytes;
- approximate active weight bytes per sparse execution step;
- minimum useful local cache;
- independently addressable page size;
- whether expert paging is supported.

This is the foundation for Jend Model Fabric / virtual weight memory.

## No magic compression claim

A generic dense 1T model at 4 bits/weight is still about 500,000,000,000 bytes
before runtime overhead. Quantization helps, but a universal 50x or 100x lossless
compression scheme for arbitrary trained weights must not be assumed.

The path to trillion-scale local *addressability* is therefore:

- sparse/MoE execution when the model architecture supports it;
- signed content-addressed pages;
- shared-block deduplication between releases/models;
- multi-tier quantization;
- SSD -> RAM -> accelerator residency;
- predictive expert/page prefetch;
- device-specific cache budgets;
- optional distillation/pruning only when the resulting changed model is
  represented as its own release.

## Storage economics

Jend does not need to run one inference server per Store model. Open/licensed
weights can live as immutable object-store/CDN chunks and be downloaded on
demand; storage/egress costs remain, but they are structurally different from
continuous GPU inference costs. Provider-backed closed models execute at the
provider unless a separate commercial hosting arrangement exists.

Future M8 Model Fabric will add content-addressed shared chunks so identical
blocks across quantizations/releases do not need duplicate physical storage.
