# M8.5.15.5 — Verified GGUF open-file identity (not native execution)

**Stage:** Backend security groundwork, development-only, no model inference.

## Problem

A pathname check followed by a new open is TOCTOU-prone. A hostile updater
may rename or replace the content-addressed path between checking the bytes
and using it. Even after a signed file is cached, merely holding a filename
does not bind an engine to the exact bytes that were checked.

## Implemented

- `inspect_independently_signed_gguf_open_file` runs the **existing**
  signed Ed25519, GGUF v3 header, exact length, ordered chunk SHA-256 and
  whole-file SHA-256 verification against a **previously opened file**.
  The public original-path inspection now delegates to this shared engine.
- `VerifiedGgufSnapshotStore::open_verified_handle` opens the local
  content-addressed filename **once**, refuses symlinks, checks regular file
  metadata and file identity where Unix device+inode metadata is available,
  and hashes the very same open file descriptor. No pass of filename to
  native C++ is authorized.
- `VerifiedGgufOpenLease` keeps a private `File` (no public raw descriptor,
  no native worker launch path). It exposes only the inspected metadata and a
  reverify operation on the exact same file description with an independently
  pinned release key.
- The offline smoke adds checked cases: signed opened descriptor succeeds;
  wrong release signer rejected; Unix path replacement leaves the held
  inode unchanged while newly opening replaced path fails; Unix same-inode
  tampering is detected on rehash. Existing six snapshot assertions remain.

## Exact security limitations

**An opened file descriptor is NOT immutable file contents.** An attacker
with write permissions to the same inode can overwrite it even while the
read-only fd is open. The rehash catches modifications only if they occurred
*before* the rehash, not changes during inference. Likewise on Windows a
File handle identifies the opened file but file-sharing rules and private
DACL policy have not been fully validated. A sophisticated hostile process
could exploit directory ancestry, mount points or in-place mutation.

**NEVER use this lease to start production GGUF inference.** The correct
future production sequence needs an OS-enforced immutable backing file or
sealed memory object, a verified/attested executable, safe handle transfer to
a no-network no-secrets native sandbox, whole-file validation over the final
OS-granted object and resource/cancellation limits. Android/iOS need
app-signed embedded engines and their own OS entitlement/capability model.

The smoke uses a synthetic GGUF-shaped header and ephemeral test signing
key, NOT a real third-party model, production publisher trust root or
complete GGUF tensor metadata parser.

## Mac offline test

```bash
cargo generate-lockfile
bash scripts/dev-verified-gguf-snapshot-smoke.sh
```

Expect 6 existing PASS lines and these additional checks:

```text
Jend GGUF same opened handle signed hash verification: PASS
Jend GGUF held descriptor rejects wrong signing key: PASS
Jend GGUF file descriptor survives pathname substitution: PASS
Jend GGUF held descriptor rehash detects same-inode tampering: PASS
```

Path substitution and same-inode tampering tests run on Unix (macOS and
Linux); Windows builds/test runs still perform the cross-platform signed
descriptor and signer checks, but the Unix pathname and chmod test is
not a Windows ACL/sandbox assurance.

## Backend-finish versus front-end start

The user wants to finish **security and backend architecture** enough to
begin building the application UI, not finish the entire Jend product.
See the root `JEND-PROJECT-CONTEXT.md` readiness gates. Design freeze
(M8.5.16) is NOT backend/security completion. A later independently
verified "Backend & Security Ready" gate is required before main frontend
implementation. P2P/remote BYOK, all GPU kernels and broad model coverage
are optional post-baseline features unless explicitly included in v1.
