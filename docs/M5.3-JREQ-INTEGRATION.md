# M5.3 — JREQ enforced DeviceSet mutation and capability refresh

`POST /v1/devices/set` now verifies the **raw HTTP body** and original
path/query before JSON parsing. The JREQ proof is supplied as one base64url
`jend-request-proof` header containing device ID, nonce, timestamp and Ed25519
signature. Duplicate Authorization or JREQ headers are rejected.

Verification order:
1. Decode JCAP and preserve its exact serialized bytes.
2. Load account and verify JCAP signature, expiry, permission, auth_epoch and
   device binding.
3. Load the current DeviceSet and require that device is still trusted.
4. Verify JREQ over method + exact path/query + SHA-256(raw body) +
   SHA-256(serialized JCAP) + device ID + nonce + timestamp.
5. For DeviceSet mutation, require `next.author == JREQ device`.
6. In one PostgreSQL transaction, lock current DeviceSet, verify epoch and
   signed transition, consume the JREQ nonce, and CAS the new DeviceSet.

`POST /v1/auth/device/refresh` is also JREQ protected. It accepts an empty
body, consumes the nonce, and reissues the same permission set; refresh cannot
escalate permissions.

## Still required before first runnable security baseline
- Apply JREQ to future sync relay/model-grant mutating endpoints when added.
- Add device-key-only session bootstrap for trusted devices after capability
  expiry, so normal users do not repeatedly enter passwords.
- Run cargo check/unit tests and PostgreSQL integration/concurrency tests.
- Add migration runner / docker-compose / CLI smoke client.
- Evaluate reverse-proxy request-target normalization before Internet exposure.

Axum 0.8 supports raw `Bytes` extraction and `OriginalUri`; this design uses
those APIs specifically to avoid signing a reserialized JSON representation.
