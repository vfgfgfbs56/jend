# M8.5.8 — Bounded Xet fetch scheduler

M8.5.8 adds transport-independent scheduling for the physical xorb fetch entries
already authenticated by the strict Xet reconstruction parser.

## Protocol rule retained

One `XorbMultiRangeFetch` remains one atomic signed request. Its ordered
`ranges[].bytes` values are encoded as a single HTTP `Range` header such as
`bytes=0-65535,200000-262143`. Jend does **not** split that signed set into
independent requests.

Different fetch entries may be assigned to bounded concurrency waves. The
scheduler preserves fetch order and gives each job a stable ordinal/wave while
logical file terms continue to be assembled in reconstruction order.

## Fail-closed budgets

The default page-fetch policy is bounded below hard ceilings:

- 64 MiB hard aggregate authorized xorb payload ceiling;
- 16 MiB hard ceiling per signed fetch entry;
- 128 fetch jobs maximum;
- 512 physical ranges maximum;
- concurrency maximum 8;
- executable Range header maximum 8 KiB.

The scheduler counts the exact sum of authorized physical byte spans. It does
not guess multipart framing overhead and does not execute the request.
Overlapping chunk coverage across separate fetch entries is rejected rather
than silently choosing one copy.

## Deliberately not implemented yet

`source_worker_transport` still exposes only the exact `SingleRange206`
contract and still rejects comma-separated Range headers there. M8.5.8 does not
parse `multipart/byteranges`, does not perform live multi-range fetches, and
does not publish a live page to WeightVM.

The next boundary is a strict multipart `206` parser that binds each returned
`Content-Range` part to exactly one planned descriptor under a bounded framing
overhead budget.
