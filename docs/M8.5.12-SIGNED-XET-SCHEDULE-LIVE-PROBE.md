# M8.5.12 — Signed Xet reconstruction schedule: realistic live probing

## Source observation

The M8.5.11 live test on Mac returned:

```text
Jend live Xet atomic multipart probe: SKIP (no eligible single signed multi-range entry; no xorb payload fetched)
```

That is a safe, expected result for a *test constrained to exactly one
multi-range entry*. It does not mean a live multi-range response was parsed
or that any physical xorb was downloaded. It does show the immutable Hub
resolve, scoped Hub read token and CAS reconstruction metadata path worked.

The Xet reconstruction schema supports multiple independent signed fetch
entries; an entry can describe one physical range or several. M8.5.12
executes that natural shape while never merging independent signed grants.

## New boundaries

- The singleton transport now strictly requires top-level `Content-Range`
  matching the exact signed byte span, status 206, identity encoding, no
  multipart fallback and the exact declared body length. Incorrect offsets
  with matching-length bodies are rejected.
- Signed single-range jobs and atomic multipart jobs are dispatched
  sequentially, one grant at a time. No retry, redirection, URL recombination
  or best-effort publication of partial results.
- The schedule is revalidated before network I/O. Its public job ordinals,
  waves, byte totals, count, per-entry signed URLs/headers and duplicate chunk
  coverage must still match the original strict reconstruction.
- A live probe of the first 1 MiB logical GPT2 safetensors is capped at 8 MiB
  aggregate physical payload, 8 jobs, 32 ranges, 128 KiB MIME overhead per
  multipart entry and 16 MiB aggregate decoded bytes. This is intentionally
  not an unlimited model download or production source-worker.
- Ineligible metadata that exceeds the probe's job/range/physical budget
  prints **SKIP** and executes no xorb traffic. Invalid authorization,
  impossible headers, wrong statuses and decompression failures hard-fail.
- Success output distinguishes `strict multipart: PASS` from
  `NOT_EXERCISED`, and separately distinguishes multiple fetch entries.
  A singleton HTTP 206 is **not described as a multipart success**.
- Any decoded result is untrusted. No on-disk raw model writes, Jend page
  signature checking, release manifest verification, WeightVM admission or
  model inference occur in this probe.

## Offline Mac check (no token)

```bash
bash scripts/dev-xet-scheduled-decode-smoke.sh
```

Expected:

```text
Jend Xet separate signed singleton entries: PASS
Jend Xet exact single Content-Range binding: PASS
Jend Xet bounded scheduled logical assembler: PASS
Jend Xet scheduled unverified bytes kept outside WeightVM: PASS
Jend Xet scheduled HTTP 200 fallback rejected: PASS
```

## Optional real HF/Xet check

Run only if explicitly authorized using an HF read-only token. The token
should never appear in logs, screenshots, commands, repository files or chat.

```bash
JEND_ALLOW_LIVE_HF_XET_SCHEDULE=1 bash scripts/dev-hf-xet-scheduled-live-smoke.sh
```

The command separately requires `JEND_HF_TOKEN` from the environment.
A success confirms a live signed HTTP 206 fetch and bounded one-megabyte
logical reconstruction, not release-signed WeightPage trust.

## Open work

M8.5.12 is a limited **developer smoke path**, not a full source sandbox,
multi-origin mirror resolver or verified independent signed page provider.
M8.6 still requires streaming range-to-page, exact signed SHA-256 + length,
trust boundary with publisher/release manifests and admission only after
cryptographic verification. The live command is not executed by GitHub CI;
only offline compilation/security tests are run there.
