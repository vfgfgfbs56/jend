# M2.5 — Registration admission, rate limits and anti-bot

Status: core implementation added; production HTTP/distributed deployment is
still pending.

## Layers

Registration admission is deliberately independent from OPAQUE authentication.
It runs *before* expensive registration work.

1. Privacy-normalized local token buckets at the Rust edge.
2. Multiple independent buckets may be applied: IP, network prefix, ASN/risk
   group and creation velocity.
3. Adaptive proof of work is zero for low-risk traffic and increases only for
   suspicious creation patterns.
4. The challenge is Ed25519-signed, short-lived and bound to the canonical
   username, so work for one username cannot be replayed to reserve another.
5. Database uniqueness is still the final username race barrier.
6. Optional provider bot/challenge signals may feed risk scoring, but no
   provider becomes the cryptographic trust anchor.

## Privacy

`jend-admission` accepts opaque `RateKey` values rather than raw IP addresses.
The production edge should derive rotating privacy-normalized keys and retain
raw addresses only as long as operationally necessary.

## Important limitation

The included token bucket is per-process/per-edge. It is not a globally
coordinated distributed rate limiter. Production must combine it with edge
limits and durable account-creation backstops; if stronger cross-region limits
are required, add a small dedicated rate-state service without putting chat or
key material into it.
