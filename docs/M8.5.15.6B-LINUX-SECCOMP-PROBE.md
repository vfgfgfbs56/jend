# M8.5.15.6b — Linux restricted native-process probe

**Status:** experimentally enforced OS syscall/resource restrictions **only**
inside the **protocol-only** C++ worker `--sandbox-probe` command on Linux
x86_64 / ARM64. This is **NOT** production native GGUF inference isolation,
a file-system sandbox, a sealed weight handle or a solution on macOS/Windows.

## What actually happens

The C++ worker includes `linux_sandbox_probe.h` only when the build
targets Linux and `JEND_WITH_LLAMA` is **not** enabled. The probe:

1. Hardens the current process with hard/soft `RLIMIT_CORE=0`,
   `RLIMIT_FSIZE=0`, `RLIMIT_NOFILE=64`,
   `RLIMIT_CPU=2s` and `RLIMIT_AS=256 MiB`. Any failure means refusal.
2. Calls `prctl(PR_SET_NO_NEW_PRIVS)` then attaches a classic seccomp BPF
   program through `PR_SET_SECCOMP`. Kernel failures mean refusal.
3. Checks the syscall ABI before applying Linux x86_64 or ARM64 rules;
   unexpected ABI calls are killed and x32-tagged x86_64 calls killed.
4. Rejects Linux network-socket creation/connection/listen/accept/send/recv,
   subprocess execution/fork/clone and ptrace through `EPERM`. Other calls
   are deliberately still allowed; do NOT interpret this as full sandbox.
5. Calls `PR_GET_NO_NEW_PRIVS`, `PR_GET_SECCOMP`, `getrlimit`, and tries
   `socket(AF_INET, SOCK_STREAM, 0)`, **requiring errno==EPERM**.
   Only then emits `JEND-LINUX-RESTRICTED-PROBE-V1`.

There is **no** automatically enabled sandbox for `--protocol-smoke` or
`--infer-dev`. The probe uses a distinct command-line argument and cannot
load weights. It does not accept a prompt or model path.

On Windows/macOS the `--sandbox-probe` entrypoint intentionally refuses
to run and prints no success marker. There is NO assumption that Linux
seccomp is equivalent to Apple's sandbox, Windows AppContainer or job
object policies. Android may use a Linux kernel, but this desktop probe is
not an Android NDK/in-app supported runtime.

## What this does NOT secure

- Without a privileged broker / mount namespace / Landlock / separate UID,
  seccomp alone does **not** prevent reads of files, E2EE secrets or other
  resources accessible to the invoking user. `read`, `openat`, `mmap`,
  `ioctl` and existing inherited file descriptors remain accessible.
- A host binary can already execute code **before** seccomp installation.
  This experiment has no independently signed worker enrollment, hardened
  loading, immutable executable identity or trusted OS launch broker.
- Linux BPF rules are a small denylist, not a complete syscall allowlist;
  side-channel and specialized IPC networking paths are not comprehensively
  blocked. Do not pass real chat plaintext or signed model bytes to this
  test.
- `setrlimit` alone does not provide aggregate child/process-tree isolation
  or kill-on-timeout. A production launch requires OS containment and
  process group/job management from an independently trustworthy parent.
- The existing GGUF snapshot path is not immutable against in-place writes,
  and there is still no race-free signed-handle adoption by native inference.
- CPU/GPU model generation is not implemented by this milestone.
- CI proves Linux x64/ARM64 actual restricted probe and Darwin/Windows
  absence, but this does not demonstrate mobile execution or production
  OS sandbox readiness.

## Offline test

From repository root with CMake, Python and a C++17 toolchain:

```bash
python3 scripts/dev-native-linux-seccomp-probe.py
```

Common lines across supported desktop hosts:

```text
Jend native security probe compiles on host: PASS
Jend native probe leaves production model execution disabled: PASS
Jend native probe proves NO filesystem or E2EE isolation: PASS
```

On **Linux x64/ARM64**, additionally:

```text
Jend Linux seccomp no-new-privs and network denial: PASS
Jend Linux finite CPU RAM open-files and core limits: PASS
```

On **macOS and Windows**, instead:

```text
Jend unsupported desktop OS native sandbox refused: PASS
```

The macOS PASS is a correct **refusal**, not a Mac sandbox. Test runs also
as a separate step in `.github/workflows/native-ipc-portability.yml` on
five desktop runners, and on Linux in `.github/workflows/ci.yml`.

## Next safe engineering gates

1. A separately trusted signed native worker release + protected installation
   and race-free load of its exact executable bytes.
2. Linux strong filesystem and namespace isolation + allowlisted open fd
   handoff + strict syscall allowlist + durable process/job supervision.
3. Native OS-specific sandbox implementations and tests on macOS and Windows.
4. Immutable release-signed GGUF artifact adoption and complete bounded GGUF
   tensor/tokenizer compatibility validation.
5. Licensed existing third-party model real CPU inference, measured on
   devices, then stable frontend API/IPC and Backend & Security Ready review.

See `JEND-PROJECT-CONTEXT.md`. Frontend starts after **Backend & Security
Ready**, NOT because a seccomp proof or architecture freeze passed.
