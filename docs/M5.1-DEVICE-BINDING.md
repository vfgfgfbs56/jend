# M5.1 — Device trust binding over HTTP

M5.1 connects the existing JESP DeviceSet trust model to the Rust HTTP gateway.

## Registration trust root

OPAQUE registration no longer creates an immediately active account. `register/finish`
creates `accounts.status=1` and returns a random 256-bit registration-only device
bootstrap secret plus the server-selected AccountId. Only its domain-separated SHA-256
digest is stored. The client signs a DeviceSet genesis containing that AccountId and
submits it to `/v1/devices/genesis`. PostgreSQL atomically verifies/consumes the
bootstrap row, inserts epoch 0, and activates the account.

Generic account capabilities cannot create DeviceSet genesis. Losing the bootstrap
before genesis currently leaves a pending account; production needs a conservative
expired-pending-account cleanup/restart policy before launch.

## Existing device binding

After OPAQUE login the gateway issues an unbound 5-minute account capability.
`POST /v1/devices/bind/start` creates a challenge bound to the capability nonce. A
private device key signs that exact challenge. `/finish` verifies the signature against
the current signed DeviceSet, atomically consumes the challenge digest, then issues a
15-minute device-bound capability.

The server never receives a device private key.

## DeviceSet transitions

`GET /v1/devices/current` returns the latest signed public trust set to an authenticated
account. `POST /v1/devices/set` only accepts transitions with an explicit expected
epoch. PostgreSQL row locking plus epoch CAS prevents concurrent transitions from
silently overwriting one another; the transition must verify under a signer from the
previous DeviceSet. Genesis is rejected on this generic route.

## Remaining gap: bearer replay

A device-bound JCAP identifies which device was proven at issuance, but it is still a
short-lived bearer object. Theft of the token during its lifetime can therefore be
replayed. M5.2 should add per-request device proof-of-possession (method/path/body
digest/capability nonce/request nonce/timestamp signed by the trusted device), plus a
short replay cache. Sync/model endpoints must require that proof rather than treating
`device_id` inside JCAP as sufficient by itself.

## Verification status

The source and SQL migrations are implemented but not compiled or executed here because
this environment has no Rust toolchain or PostgreSQL client/server. Do not use it for
real secrets until cargo, DB concurrency, replay, fuzz, and adversarial tests pass.
