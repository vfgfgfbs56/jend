# M5.4 — Headless registration smoke harness

The repository now contains:
- `server/jend-migrate`: a separate SQLx migration binary. The runtime gateway
  role does not need DDL privileges after provisioning.
- `client/jend-cli`: a development-only in-memory device smoke client.
- `deployment/docker-compose.headless.yml`: PostgreSQL for localhost testing.
- a normalized, unique SQLx migration sequence.

## Intended first-run sequence

```bash
docker compose -f deployment/docker-compose.headless.yml up -d
export DATABASE_URL='postgres://jend_dev:jend_dev_only_change_me@127.0.0.1:54329/jend'
cargo run -p jend-migrate
cargo run -p jend-keygen -- ./.jend-dev-secrets
export JEND_SECRET_DIR="$PWD/.jend-dev-secrets"
export JEND_GATEWAY_ADDR='127.0.0.1:8080'
cargo run -p jend-gateway
# second terminal:
cargo run -p jend-cli -- smoke-register http://127.0.0.1:8080 alice
```

The smoke command exercises:
1. admission + proof of work;
2. OPAQUE registration;
3. one-time first-device bootstrap and signed genesis DeviceSet;
4. OPAQUE login;
5. device binding and device-bound capability;
6. JREQ-signed `GET /v1/devices/current`;
7. JREQ-signed device capability refresh;
8. capability-free trusted-device session challenge/proof;
9. a new device capability and another JREQ-signed request.

The generated device identity exists only in process memory and is discarded at
exit. Production persistence belongs to `jend-vault`.

## Security properties of the headless path

A stolen device capability is insufficient for the implemented device routes:
`/v1/devices/current`, `/v1/devices/set`, and `/v1/auth/device/refresh` require a
fresh JREQ Ed25519 proof from the currently trusted device. DeviceSet mutation
consumes the JREQ nonce in the same PostgreSQL transaction as the epoch CAS.

After a short-lived capability expires, a trusted device can obtain a new one
through `/v1/auth/device/session/start` + `/finish` using a fresh server
challenge and its device private key. No password is required. Revoked devices
fail because finish verifies membership in the current signed DeviceSet.

## Not production deployment

- localhost HTTP is acceptable only for this smoke harness; Internet exposure
  requires TLS and carefully tested reverse-proxy request-target handling;
- the development PostgreSQL credential is intentionally non-production;
- pin container image digests before production;
- use separate migration/runtime DB roles;
- future sync/model mutating endpoints must also require JREQ;
- cargo compilation and PostgreSQL integration/concurrency tests are still
  pending in the current environment.
